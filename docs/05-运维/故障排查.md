# 故障排查

## 「模拟输入/输入源/录制」按钮点了没反应

1. 看界面顶部有没有红色告警条(原生模块加载失败)
2. 命令行看日志:
   ```bash
   grep "\[native\]" /tmp/app.log     # 或从终端启动 App 直接看输出
   ```
3. 检查安装包:
   ```bash
   node tools/verify/verify-package.cjs "/Applications/模拟输入.app"
   ```
   看「原生模块已解包到 app.asar.unpacked」是否 ✅
4. 常见原因:**只换了 app.asar 没换 app.asar.unpacked**(见 ADR-0003)

## Safari 复制修复不生效

> 下面这套步骤是 **Tauri 版**的。Electron 版的数据目录、诊断文件、脚本都不一样,
> 别把两边的命令混着用(2026-10-22 这次排查就被 Electron 的路径带偏过)。

按顺序排查:

1. **功能开关是否开着**:界面「Safari 复制修复」= 开启
2. **App 是不是退出了**:关窗口不该退出(macOS 惯例)。看进程:
   ```bash
   pgrep -fl simuinput-tauri
   ```
3. **目标页有没有被接管**:页面上应有 `window.__copyRepairGuard`。查:
   ```bash
   osascript -e 'tell application "Safari" to do JavaScript "String(!!window.__copyRepairGuard)" in tab 1 of window 1'
   ```
   - `false` → **守卫根本没装上**(注入失败),看第 5 步的 `lastError`
   - `true` → 守卫在,继续看第 4 步
4. **映射有没有送到页面**:守卫里 `window.__copyRepairGuard.mappings` 应有内容;
   复制时若打出 `copy-no-mapping`,就是映射没到(看第 5 步的 `mapping` 字段)
5. **看诊断文件**(字段含义见下):
   ```bash
   cat "$HOME/Library/Application Support/com.gojocloud.campus-network-connector.tauri/diag.json" | python3 -m json.tool
   ```
   - `safariRepair.enabled` — 开关状态
   - `safariRepair.injected` — 这一轮有没有处理到标签
   - `safariRepair.lastError` — 致命错误(权限/注入失败/参考库缺失)
   - `safariRepair.mapping` — **映射没建起来的原因**(取字体失败/分析失败/映射为空);
     这三种以前全是静默跳过,只看 `enabled` 会以为一切正常
   - `safariRepair.mappingScopes` — **逐个作用域**的映射结果(保留 12 条);
     只留"最后一次"会把真正出问题的那条盖住(页面上常有五六个作用域)
   - `safariRepair.safariRunning` — Safari 在不在跑(`false` = 没开,中性状态不是错误)
   - `safariRepair.runningProbe` — **判活查询的原始结果**;
     看到 `查询失败: …` 就说明判活这一环断了(见下面第 7 步)
   - `safariRepair.poll.lastProbe` / `pollCount` — 轮询看到几个标签、还在不在跑

> ⚠️ **`diag.json` 是前端每 3 秒写一次的快照。**
> App 窗口不可见时,WebView 的定时器会被系统节流 → **文件停在旧值**,
> 看着像「功能死了」其实是「界面没在刷新」。
> 排查时先把 App 窗口亮着再看这个文件(2026-10-22 就被这个坑过一次:
> 误以为后台轮询线程死了,其实它好好地在跑)。

6. **是不是没等到映射**:刚打开页面 1 秒内复制可能还没建好映射 → 等 2 秒再试
7. **判活查询是不是断了**(2026-10-23 真实故障,ADR-0015):
   老口径问的是 `System Events`,那要**另一份**自动化授权,
   用户从来没被提示过 → 查不到 → 被判成"Safari 未运行" → **整个功能静默停掉**。
   症状是:`lastError` = "Safari 未运行"、`poll.lastProbe` **全空**、
   但 Safari 明明开着很多标签。现在改用 `application "Safari" is running`,
   `runningProbe` 字段会直接显示查询结果;再不行就查
   **系统设置 → 隐私与安全性 → 自动化** 里有没有本 App 对 Safari 的授权。

### 换题后立刻复制,还是密文(等约 0.4 秒就变明文)

**这不是功能坏了,是分析还没完成。**
换到**全新字体**(新的 data URI)时,字体分析要重跑一遍:
原先串行很慢(当时实测 11 秒),并行化之后更快。
⚠️ **那两个数是 debug 构建量的**:release 下同一份真机字体只要 **13ms**(debug 慢 25 倍)。
**所以"等分析"从来不是等 2 秒的原因** —— 真正的原因是**映射下发**要 2 秒(见 ADR-0016)。
这段时间里页面上一份映射都没有 → 复制出来必然是密文。

- 已缓存的字体 → 立即可用
- 全新字体 → 稍等再复制。**现在正常的等待是 0.1~0.5 秒**(实测:87~532ms 就能出明文);
  超过 **1 秒**还不行,查 `safariRepair.fastPoll`(快通道是不是活着、有没有盯住那个标签)
- 换题**不换字体** → 映射直接复用,没有这个窗口

### 换题后第 1 次复制成功、第 2 次复制出密文(ADR-0017)

**先分清是哪种"密文"**:

- **整段都是密文** → 是"这个作用域的映射压根没建起来" → 看下面第 4 步
- **字是乱的但顺序对** → 那是**写错字**,属于更严重的一类 → 见"宁可留错字,绝不写错字"

这一轮在真机上查到**三个根因**(ADR-0017 有完整推导)。现场怎么认:

| 现场现象 | 根因 | 怎么一眼看出来 |
| --- | --- | --- |
| **App 重启后,页面不再上报已有的作用域** | 「送到了就不重报」**用错了账本**:拿页面的 `mappings` 判断"App 知不知道" | 页面里 `window.__copyRepairGuard.deliveredAt` 是空的、`mappings` 却有值 → App 永远学不到 → 快通道是瞎的 |
| **换题后守卫扫到 0 个作用域**(`pageScopes=0`) | 站点顺序是"先注入 @font-face → 再渲染题目文字",签名先到 → 这次扫到 0 个 → 之后签名不再变 → **永远不再重扫** | 手动把 `window.__copyRepairGuard.fontSig` 清空再扫一次,**立刻就发现了** → 说明是**触发条件**的问题,不是字体读不到 |
| **新题目的作用域沿用了旧字体的映射** | 字体指纹用**取样哈希**,而混淆字体"结构相同、字形不同" → 撞车 | 作用域 key 里的指纹:真机上**同一份字体**,取样是 `datagi2tog`、整份是 `data2cozfw` |

**现场能做的三件事**:

1. **App 学到这个作用域了吗**:`diag.json` 里 `safariRepair.fastPoll.cipherTabs` 应 ≥ 1。
   为 0 → **没有作用域被登记进快通道**(多半就是第一个根因)。
2. **页面在持续上报吗**:`window.__copyRepairGuard.reportedAt` 应该**一直在动**。
   App 重启后如果它卡住不动 → 就是"App 知不知道"这本账没被清(第一个根因)。
   `deliveredAt` 有值 → App 已经确认过 → 页面**不会**再报(这是正常状态)。
3. **指纹是整份哈希吗**:换两次题,作用域 key 里的指纹应当**跟着字体变**;
   两次一模一样 → 撞车了(取样哈希)。

**修完之后的验收口径**(真机,真实学习通作业页):换题后复制 **0/4 密文**(和参考明文比),
快通道周期 **205ms**(工作 110ms),映射从零到页面 **116~705ms**。

### 守卫日志里找不到「这次复制走了哪条路径」(日志被 pending 冲光)

**症状**:想查某次复制走的是 `copy-repaired` 还是 `copy-no-mapping`,
但守卫日志里**一条复制记录都没有**,只剩下一堆 `pending`。

**原因**:日志是 **200 条的环形缓冲**。'pending' 是**每轮**都会发生的事
(App 还没确认过 → 每轮重报),每轮都记一条的话,三十来秒就把缓冲冲光。

**现在的行为**(ADR-0018 之后):'pending' **内容没变就不重复记**,变了才记一条。
所以正常情况下日志里 `pending` 只有一两条,复制记录不会被挤掉。

**如果还是被冲光**,按这个顺序查:

1. **页面里的守卫是第几版**:
   ```bash
   osascript -e 'tell application "Safari" to do JavaScript "String(window.__copyRepairGuard && window.__copyRepairGuard.version)" in tab 18 of window 1'
   ```
   版本比 App 里的旧 → 页面还留着旧版守卫(旧版每轮都记 pending)→
   等 App 重新注入它(每 5 轮一次,约 1 秒),或直接刷新那个标签页。
2. **是不是还有作用域一直没被 ack**:看 `reportedAt` 与 `deliveredAt` 的差集。
   差集里剩下的就是 App 还没确认过的作用域 —— 每一个都会每轮重报。
   - `...#nofont` 的普通字体 → **正常**(新版守卫根本不上报它们)
   - `...#<哈希>` 的混淆字体 → App 侧在处理它(看 `safariRepair.mapping` 的失败原因)
3. **App 侧的失败原因**:`safariRepair.mappingScopes` 里逐条写着
   「取字体失败 / 分析失败(负缓存) / 映射为空」。
   分析失败进负缓存 → 10 分钟内不再重试 → 这段时间里那个作用域会一直重报。

### 复制出来还是密文,但守卫明明在(看守卫版本对不对)

页面上可能留着**上一任 App 注入的旧版守卫**。守卫自己能按版本号就地升级,
但**前提是有人重新注入它**。

- **Tauri 线**:每 5 轮强制重注入一次 → 版本一变就升级(约 1 秒内)
- **Electron 线**:现在会**直接比对版本**,对不上就立刻重新注入

查版本的办法同上一条第 1 步。**版本对不上却一直没换**,说明重新注入这条路断了
(注入失败会记在 `safariRepair.lastError`)。

### 守卫装上了,但复制出来还是密文

看 `safariRepair.mapping` 字段:

- `取字体失败(url): …` — 字体下载不到(跨源/需要鉴权/地址变了)
- `分析字体失败: …` — 拿到的不是合法字体文件
- `映射为空(字体 N 个码位,都没认准)` — 字体不是混淆字体,或识别置信度不够
  (置信度不够时**故意不改** → 宁可留怪字,绝不写错字)

## 复制出来的还是怪字,但界面显示正常

说明字体识别失败。查:

- 该作用域的字体是否可读(`@font-face` 在跨源样式表里就读不到 → 不还原)
- 识别置信度不够时会**故意不改** → 宁可留怪字

## 复制只修好一半(前半句明文、后半句密文)

这是 2026-10-21 修掉的真实故障(根因见 ADR-0005):查表要两样东西,
"这个字画成了哪个字"来自主进程的映射表(按字体整份下发,不会过时),
但"这个字属于哪个字体作用域"曾经是**采集缓存**——采集比复制慢一拍,
于是**刚选到、还没采集过的新密文字**查表落空 → 原样进剪贴板。
早先选过的字在缓存里 → 修好了(所以看起来"只修好一半")。

**现在复制时当场按当前选区解析作用域,不再依赖缓存。**
如果又出现同样现象,先确认页面里的守卫版本:

```bash
node tools/lab/diag-frames.cjs chaoxing        # 看每层 frame 的守卫状态与作用域
node tools/lab/diag-apply.cjs <tab> judge      # 逐字复算查表路径,看是谁落空
node tools/lab/verify-fastcopy.cjs --tab <tab> # 清空采集缓存后立刻复制,必须全还原
```

`verify-fastcopy.cjs` 是这个故障的**回归测试**:它清空采集缓存再复制,
旧守卫会红(剪贴板留原样密文),新守卫必须零残留。

## 换页时内容区底下有条横条在动

那是**横向滚动条**,不是步骤圈之间的进度线(那条在**上面**)。

- 现象:界面 1 ↔ 2/3/4 切换时,内容区**底下**淡入一条横条,滚块跟着画面移动。
- 根因:内容容器写的是 `overflowY: 'auto'`。按 CSS 规范,一个轴是 `auto` 时,
  另一个轴的 `visible` 会被**算成 `auto`** → 横向其实也能滚;
  切页时正在退场的那一页往右滑(`x: '50%'`),横向就溢出 → 底部冒出横向滚动条。
- 判据:内容容器的计算样式必须是 `overflow-x: hidden`(纵向仍要是 `auto`)。
- 验证:`node --test tools/verify/verify-panel-transition.cjs`
  —— 它会逐帧确认「确实有横向溢出」且「确实有层在横向移动」(动画没丢),
  再把 `overflow-x` 改回 `auto` 复测,证明这条断言**有判别力**。

> ⚠️ **别当成「高度上限」的问题去改**:`maxHeight: '65vh'` 历史上被去掉过
> (`c4612e5`)又被搬回来(`f9d3bbf`),但这条滑条在那段时间里**同样存在**。
> 要治的是**横向溢出**。

## 录制时点自己界面上的按钮,被记成了一次点击

- 现象:点「结束」按钮之后,录到的点击里多了一条(坐标就是按钮的位置)。
- 根因(两个都真):
  1. **排除矩形是废的**:WKWebView 里 `window.screenX / outerWidth / outerHeight`
     实测是 `0 / 0 / 0` → 传给原生的矩形是空的一条线,**一次都没排除过**。
     (Electron 侧这几个值是准的。)
  2. **那张快照会过期**:Tauri 的窗口贴合内容,内容变高时窗口**向上长**
     (Cocoa 的 `setContentSize` 固定的是左下角)→ 「结束」按钮移出了开始时的矩形;
     窗口被拖动同理。
- 现在的口径:排除矩形由**原生层**算,并在窗口每次移动/变高时刷新
  (Tauri 监听窗口事件;Electron 监听 `move`+`resize`),前端不再传。
- 查:运行自检 `diag.json`:
  - `native.recordingExcludeRect` —— 当前的排除矩形(应与窗口实际位置大小一致);
  - `native.recordingExclusionCheck` —— 自检结果(见下)。
- 自检(带参数启动):

  ```bash
  # Tauri
  open -a /Applications/模拟输入-Tauri.app --args --diag-recording-exclusion
  # Electron(结果写在 <userData>/diag-recording.json)
  open -a "<模拟输入.app>" --args --diag-recording-exclusion
  ```

  结果里 `control` = 关掉排除时记下的条数(应为 1),
  `excluded` = 打开排除时记下的条数(应为 0),
  `conclusive` = 这次有没有结论。

  ⚠️ **必须用 `open -a` 启动**:从终端直接跑二进制会拿不到辅助功能身份,
  合成点击被系统丢掉 → `control: 0` → `conclusive: false`。
  那是**启动方式**的问题,不是代码的问题 —— 别照着改代码。

## 按一次快捷键,App 整个崩掉(2026-10-23)

- 现象:按 ⌃⇧A / ⌃⇧D 之后 App **当场消失**(不是报错退出,是进程被打死);
  再打开一切正常,但**再按又崩** ⇒ 这条快捷键整体不可用。
- 根因:**Carbon 的文字输入源 API 只能在主线程调**。
  快捷键的**事件 tap 回调线程**(`cnc-hotkey`)在记命中时顺手读了一次
  当前输入法 → Carbon 内部 `dispatch_assert_queue` → **SIGTRAP** → 进程死。
- 怎么查:崩溃报告在 `~/Library/Logs/DiagnosticReports/simuinput-tauri-*.ips`,
  看 `faultingThread` 是不是 `cnc-hotkey`,栈里有没有
  `TSMGetInputSourceProperty` ← `processEventTapData`。
- 现在的口径:所有 Carbon TIS 调用都**编排到主线程**(`commands::native::run_on_main_thread`),
  并且有一道**守卫**——跑错线程就报错,绝不硬调 Carbon。
- 自检(**零副作用**,不发任何系统级事件):

  ```bash
  open -a /Applications/模拟输入-Tauri.app --args --diag-hotkey-trigger
  ```

  结果在 `diag.json` 的 `shortcuts.hotkeyTriggerCheck`:
  `probeThreadRead` = 从非主线程读输入源是否正常(应为 `true`)、
  `hitRecorded` = 命中有没有被记下、`lastHit.inputSource` = 输入源有没有被回填。

  ⚠️ **这个自检以前会往系统里发一个真的 ⌃⇧A,导致机器卡死**,
  现在改成了「只在自己进程内走一遍那条会崩的代码路径」。
  见 ADR-0021。

## App 反复点自己的「默认执行」、疯狂敲键盘、机器卡死(2026-10-23,T0)

- 现象:App 自己在反复点界面上的「默认执行」,键盘一直在响,
  整台机器卡死,最后只能**强制关机**。
- 根因是**一条自激环路**(见 ADR-0021):
  回放发出的**合成点击**落在 App **自己的窗口**上 → 点中自己的「默认执行」→
  又一次回放 → 再点自己 → 无限循环;而且回放**没有重入保护**,
  一次触发能并行起成百上千个回放线程 ⇒ 疯狂敲键盘。
- 现在的口径(两道闸,两边同口径):
  ① **重入保护**:同一时刻最多一个回放,后来的直接拒绝(界面会提示
     「上一次回放还没结束,这次没有重复执行」);
  ② **回放不打到自己窗口**:落点在自己窗口内的点击**不发出去**(计入 `skipped`)。
- 查:`diag.json` 的 `playback`:
  - `playing` —— 现在有回放在跑吗;
  - `rejected` —— 因为"已经在放了"被拒绝过几次(正常用应该一直是 0);
  - `skipped` —— 上次回放里有几条因为落点在自己窗口上被丢掉;
  - `guardCheck` —— 最近一次两道闸的自检结果。
- 自检(**零副作用**):

  ```bash
  open -a /Applications/模拟输入-Tauri.app --args --diag-playback-guard
  ```

  造的落点全在自己窗口内,并且**先断言**它们确实会被丢掉 ——
  断言不过就直接报错、不起回放,所以**不会有任何点击发到屏幕上**。

## 快捷键按了没反应 / 突然多打出一个 D(2026-10-23)

- 现象一:按 ⌃⇧A / ⌃⇧D,动作没执行(「默认执行」没回放、剪贴板没直输)。
- 现象二:按了快捷键,前台应用里**多出一个 D**(或 A)这类字符。
- 根因(2026-10-23 定位):Tauri 线的快捷键 tap **从来没吞掉过按键** ——
  core-graphics 里 tap 回调返回 `None` 是**放行**、不是"丢弃",
  老代码注释写的「返回 None = 吞掉 ⇒ 不会多打出 D」是错的。
  于是每次组合键都**完整漏给前台应用**;修饰键没被识别成完整的 ⌃⇧ 时,
  前台收到的是 ⇧D ⇒ 直接打出大写 D。详见 ADR-0022。
- 已修:命中时把事件类型改成 `Null` 再交回去(这才叫"丢弃");
  长按的自动重复、配套的 keyup 也一并吞掉。
- 查:`shortcut-hits.json`(app 数据目录,**每次命中都会立刻写**)
  - `hits` 里有没有这次的记录?—— **没有** = 系统没把组合键送来
    (tap 没起来 / 修饰键不对 / 那个键根本不是 A、D);
  - `outcome` 是什么?
    - 「命中(按键已吞掉)」= 认出来了,动作已触发;
    - 「开始回放 X」= 回放起来了(去查 `diag.json` 的 `playback`);
    - 「上一次回放还没结束」= 被重入保护挡了;
    - 「X 里没有可执行的点击」/「一个录制文件都没有」= 没东西可放;
  - `flags` = 那一下的修饰键位(`0x40000`=Control、`0x20000`=Shift、
    `0x100`=NonCoalesced;缺 0x40000 就是 Control 没被识别);
  - `inputSource` = 当时的输入法(非 ASCII 时中文候选框会吃掉按键)。
- 另查:`diag.json` 的 `playback` 段 —— `executed` / `skipped` / `error`。
  落点在自己窗口上、且窗口穿透失败时,那些点击会被**跳过** ⇒
  看起来同样是"按了没反应"。
- **Electron 线还没修**:它用系统热键,修饰键对不上就照漏(当年的投诉两个版本都有)。
  根治要改成自建 tap,本轮没做。

## 快捷键要三个键「同时」按才有反应(2026-10-23)

- 现象:⌃⇧A / ⌃⇧D **必须三个键同时按下去**才触发;差一点点(有先后顺序、
  手上有偏差)就完全不响应,有时还会往前台漏一个 A / D。
- 根因:判定只看**主键 keydown 那一瞬间事件自带的 flags**,没跟踪修饰键状态。
  三个键几乎同时落下时,硬件扫描顺序可能让**主键的事件先于**修饰键的
  `FlagsChanged` 到达 ⇒ 那一刻 flags 还是空的 ⇒ 匹配不上 ⇒ 既不触发、
  又漏给前台。详见 ADR-0023。
- 已修:自己跟踪修饰键状态(`FlagsChanged`),判定用「跟踪到的 ∪ 事件自带的」;
  修饰键**后补齐**时回头认已经按下的键 ⇒ **按下顺序不再影响触发**。
- **怎么按最稳**:**先按住 ⌃⇧,再按 A**(修饰键先到 ⇒ 主键事件自带完整 flags
  ⇒ 匹配 ⇒ 被吞掉 ⇒ **一点都不会漏**)。三个手指同时砸也能触发,但那一键
  仍可能漏出去一次(macOS 的事件流已经过去了,追不回来)。
- ⚠️ **⌘⇧A 也会被认成「默认执行」**,而 ⌘⇧A 在 Chrome/Safari 里是
  「新建标签页」—— 会被抢。界面文案写的是 `Control+Shift+A`,严格说该只认 ⌃⇧,
  但收窄能力要单独授权,所以暂未改。
- 查:`shortcut-hits.json` 的 `hits`(见上一节)——
  有记录 = 认出来了;没记录 = 系统没送来或修饰键不对。

## 快捷键改成了 ⌃S / ⌃D,按住 Ctrl 连按不再连着触发(2026-10-23)

- 新键位:**⌃S** = 默认执行(回放)、**⌃D** = 读剪贴板并键入。
  - **只认 Control**:⌘S / ⌘D **不触发**(那是系统的「保存」「书签」);
  - **不要求 Shift,但带 Shift 照样触发**(容错)。
- latch:触发一次就被**消费掉** —— Control 不松开,再按字母
  **既不执行动作、也不往前台漏键**;**必须松开 Control 再重新按住**才恢复。
  详见 ADR-0024。
- 怎么查:
  - `shortcut-hits.json` 的 `hits` —— 每次**真正触发**记一条。
    「按了没反应」时:只有一条记录 ⇒ latch 生效中(Control 还没松开);
    完全没有记录 ⇒ 系统没送来 / 修饰键不对。
  - `diag.json` 的 `shortcuts.tap` —— tap 是不是活的;
    `shortcuts.tap.latchArmed` —— latch 现在是不是武装着:
    `true` = 没锁着(那"按了没反应"就是别的原因);
    `false` = 还锁着(Control 一直没松开 ⇒ **这是设计如此**)。
- ⚠️ **Windows 包还没换**:Windows 走 `win` 分支,那边仍是 ⌃⇧A / ⌃⇧D,
  而且**没有 latch**(Windows 线拿不到 Control 的边沿)。
  这是**平台差异**,不是坏了。
