# ADR-0014:注入脚本里的字符串字面量必须按 JSON 编码,不许直接拼源码

- 状态:已定
- 日期:2026-10-22
- 相关:ADR-0001(用 Apple Events 注入而非 Safari 扩展)、ADR-0013(界面层逐字照搬 Electron)

## 背景

2026-10-22 真机排查「**新版本**的网页(Safari)修复功能没生效」:界面上的问号是绿的、
显示「已开启」,但复制出来还是密文。

用户的猜测是「和 Electron 那边内存没协调好」。**这个猜测是错的** —— 两版守卫脚本
(`page-guard.js` / `frame-bridge.js`)逐字相同,注入逻辑各自独立,不存在互相干扰。

逐层定位后坐实的根因:

1. 页面上 `window.__copyRepairGuard` **压根不存在** → 守卫从来没装上过,
   所以也不可能建出映射、更不可能还原文字;
2. 守卫脚本本身没问题(手动把源码 `do JavaScript` 进去,立刻就装上了);
3. **问题出在"怎么把守卫源码拼进注入脚本"这一步**:

   Rust 侧 `inject_guard` 把守卫源码**原样**拼进 `{ guardSource: "..." }` 的
   JS 字符串字面量里。守卫源码本身是一份 JS 文件,里面全是 `"` 和 `\` ——
   **第一个引号就把字面量提前闭合,整段脚本变成 JavaScript 语法错误**,
   `do JavaScript` 整段失败,连前面那句合法的守卫代码也一起不执行。

4. 这个错误当时还被 `let _ = bridge::inject_guard(...)` **吞掉了** ——
   于是界面只显示「已开启」,没有任何报错,看着像"功能开着但不工作"。

Electron 版没这个问题:它用 `JSON.stringify(...)` 嵌守卫源码。
也就是说,**两个守卫文件逐字相同并不代表行为相同** —— 调用方(拼接方式)被改错了。

## 候选方案

| 方案 | 优点 | 缺点 | 结论 |
| --- | --- | --- | --- |
| A 守卫源码用 JSON 字符串编码后再嵌进字面量(`serde_json::to_string`) | 与 Electron 版**同口径**;JSON 字符串就是合法 JS 字符串,不可能再拼崩 | 无 | **选它** |
| B 守卫源码走 base64 传输,页面侧 `atob` 还原 | 彻底绕开转义 | 与 Electron 版口径不一致;多一层编解码;改动面更大 | 不选 |
| C 把守卫源码拆成多段字符串再拼 | 不用整体转义 | 拼接逻辑更复杂,转义照样要处理 | 不选 |

## 决定

1. `bridge::build_inject_script` 用
   `serde_json::to_string(&to_ascii_js(guard_js))` 嵌入守卫源码
   —— 与 Electron 的 `JSON.stringify(toAsciiJs(guardSource))` **逐字同口径**。
   顺序不能反:先转义非 ASCII(AppleScript 按本地编码解码),再做 JSON 编码。
2. **注入失败不许被吞**:除「AppleScript 超时」(页面正忙,守卫可能已装上)外,
   注入错误一律冒到 `last_error`,必须能在界面/诊断里看见。
3. **映射没建起来的原因必须透出**:取字体失败 / 分析字体失败 / 映射为空
   这三条分支原本都是静默 `continue`,现在各记一条原因到 `safariRepair.mapping`。
4. 回归测试两道:
   - 注入脚本里 `guardSource:` 的字面量必须是**合法 JSON 字符串**(能解析回原文);
   - 用仓库里**真实的守卫文件**拼出的整段脚本,必须能被 `node --check` 解析。
5. 界面上的「**已接管**」必须是**真实口径**:必须有标签的守卫确实在场,
   不能是"这一轮处理过至少一个标签"。
   —— 这正是这次故障最误导人的地方:守卫一次都没装上,界面照样显示「已接管」。

## 代价

- 注入脚本比之前长(多一层转义),但仍是同一个 Apple Event,没有额外往返。
- 诊断里多一个字段(`safariRepair.mapping`),前端不展示、只落 `diag.json`。

## 验证

- `cargo test --lib` 11/11(含新增的 4 个注入相关测试)。
- `node --check` 对真实守卫拼出的注入脚本:通过(修复前是 `Unexpected token ';'`)。
- 真机(Safari + 本地混淆样例页):修复前 **18 个标签一个都没装上守卫**;
  修复后样例页 `window.__copyRepairGuard` 存在,守卫日志 `installed → prefetch → pending`,
  映射 **132 个字**,剪贴板是明文「人工智能正在改变世界科技」,与真值表逐字一致。
- 界面状态:修复后 `injected`(=已接管)= true;注入失败时它会回到 false,
  并由 `lastError` 带着「注入守卫失败: …」显出来(界面红字那行)。

## 附带发现(同一轮排查里查实的,不是本次改动)

- **`diag.json` 是前端每 3 秒写的快照**:App 窗口不可见时 WebView 定时器被系统节流,
  文件会停在旧值 —— 看着像「后台线程死了」,其实它好好地在跑。
  排查时必须先把窗口亮着再看这个文件。
- **Safari 里大部分标签的脚本上下文是 `about:blank`**(标签地址还在,但文档上下文是空的),
  `do JavaScript` 在这种标签上等于白跑。真实的 `i.chaoxing.com` 标签是好的。
