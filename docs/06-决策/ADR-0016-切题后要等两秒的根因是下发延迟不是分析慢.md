# ADR-0016:切题后要等两秒 —— 根因是「下发延迟」,不是「分析慢」

- 状态:已定
- 日期:2026-10-23(晚)
- 相关:ADR-0015(真实站点三处断点)、ADR-0011(明文不在浏览器里与换题时间窗)、
  ADR-0002(映射按字体建而非按选区)

## 背景

ADR-0015 修完三处断点后,用户复测:

> 这次效果比刚才要好,但是依然是两三次中间出现了一次错误,
> 我怀疑,现在高度怀疑是因为它需要的时间还是偏长。

**"两三次里错一次"** —— 这个失败率 ≈50%,而且是**有周期的**,不是随机故障。
一个随机故障不可能这么规整。

## 一、先把"分析慢"这个猜测排除掉

用户的猜测方向是"时间偏长",但**慢的不是分析**。
2026-10-23 晚,在**同一份真机字体夹具**(`src/features/safari-repair/test/fixtures/live/`
下那两份,就是从真实学习通页面抓的)和**同一份参考库**(21517 字、48×48 精细栅格、
8×8 粗栅格)上,把两个引擎逐段量了一遍:

| | Electron(Node/JS) | Tauri(Rust,release) |
| --- | --- | --- |
| 栅格化 | 0.51~0.64 ms/字 | **0.037 ms/字**(快 14~17 倍) |
| 最近邻查找(单核) | 5.1~5.7 ms/字 | **3.0~3.1 ms/字**(快 1.7 倍) |
| 整份字体分析完 | 157ms(25 码位)/ 248ms(44 码位) | **13.4ms / 23.0ms** |

**Rust 版比 Electron 快 12 倍。** 分析根本不是瓶颈。

> ⚠️ **顺带更正 ADR-0015 里的一个数**:"字体分析 11 秒 → 2.5 秒"那两个数是
> **debug 构建**量的。同一份字体:debug 354ms vs release 13.4ms —— **差 25 倍**。
> release 下分析一份真机字体只要 13ms。那个"2.5 秒"从来不是用户等的东西。

## 二、真正的瓶颈:映射**下发**要 2 秒

一次 Apple Events 往返实测 **≈110ms**(每次都新起一个 `osascript` 进程;
25KB 的注入脚本也一样,体积不影响耗时,**只影响次数**)。

而 Tauri 版的轮询是**一条串行通道**(`repair.rs` 的 `spawn_poller`):

```
每 300ms 一轮(单线程,顺序做):
  1. 判活 application "Safari" is running      → 110ms
  2. 列全部标签的 URL                          → 110ms
  3. 目标站点标签 **每 2 轮**才处理一次          → 实际 ~1 秒才看一眼
  4. 每个标签: poll_state(110ms) → 分析(13ms) → set_mapping(110ms × 作用域数)
```

Electron 版有**两条通道**:主轮次一圈 1.4 秒,外加一条**独立的快轮询**
(`coordinator.js` 的 `fastTick`):**200ms 一次**,只盯"出现过混淆字体的标签",
**不判活、不列标签**。它自己的注释写着:

> 它独立于主轮次(不共用 running 标志),否则主轮次一圈 1.4 秒会把快轮询饿死。

**Tauri 版移植时把这条通道压成了单通道。** 这就是"快的变慢"的全部原因。

### "两三次错一次"从哪来

目标标签**每 2 轮**才被看一眼 → 用户切题的时刻,大约一半落在"还没轮到"的那一轮
→ **失败率天然接近 50%**。它不是随机故障,是"每 2 轮"的周期规律。

## 三、决定:补一条同形状的快通道

照搬 Electron 版 `fastTick` 的形状:

1. **快通道线程**:200ms 一轮,只处理**建出过映射**的标签
   (= 真的用了混淆字体)。图标字体(icomoon)建不出映射、也不会换题,
   让它进来只是白花 Apple Event。
2. **不判活**:读主通道的状态(它每轮都在问),不额外发 Apple Event。
3. **不列标签**:只按登记的 (窗口,标签) 直接去取。
4. **标签被关掉(`-1728`)才摘掉**;超时**不摘**(页面忙 ≠ 标签没了)。
5. **主通道让位**:快通道盯着的标签主通道不重复处理(省两次 Apple Event)。
   但快通道靠**心跳**证明自己活着 —— 线程死了主通道**自动接管**回来,
   不能就此不再管那些标签。
6. **同一个标签只允许一条通道处理**:主/快两条通道都调 `check_tab`,
   用处理权锁互斥。否则两次注入/下发会互相覆盖,而先发的那次 Apple Event
   还在等页面返回 → 偶发的"映射丢了"。

### 顺带修的一处浪费

`FastGlyphMatcher::new` 要**克隆整份 9.7MB 的库**并重建粗栅格索引(1.4MB)
+ 精确哈希索引,实测 **36ms/次**。而 `check_tab` 每次都重建一遍 ——
快通道 200ms 一轮,每次重建就是纯浪费(还会让整台机器发烫)。
改成**全局只建一次**(Electron 版是 `engine.matchers` 这个 Map,本来就只建一次,同口径)。

## 四、实测(真机,真实学习通测验页,题目在第 4 层同源 iframe)

测法:清空所有 frame 的映射 + 撤掉选区(让守卫走**预取**路径重新上报),
然后轮询**题目那层 frame 的 mappings 条数**,从 0 变成 >0 的那一刻 = 映射到了页面。

**同一台机器、同一个页面、同一个探针、同样的安装流程,唯一差别 = 有没有快通道:**

| | 改之前 | 改之后 |
| --- | --- | --- |
| 映射下发耗时 | 1605 / 2379 / 2619 / 2173 ms | **87 / 403 / 532 / 258 / 563 / 396 / 409 / 390 / 420 / 397 ms** |
| 均值 | **≈2194ms** | **≈320ms**(快 **6.9 倍**) |
| 端到端复制 | 常常复制出密文 | 剪贴板**无残留密文字**(6/6 次) |

诊断新增 `safariRepair.fastPoll`(盯着的标签数 / 心跳 / 是否活着),
现场能直接看到 `{"alive":true,"cipherTabs":1,"heartbeats":20,"intervalMs":200}`。

## 五、回归测试(+4)

- `快通道的登记与摘除`
- `同一个标签只允许一条通道处理`
- `主通道让位给快通道_快通道死了要接管` ← 快通道死了主通道必须接管
- `目标站点标签每两轮才进主通道`

`cargo test --lib` 16/16。

## 六、没做的(以及为什么)

- **`set_mapping` 合并多个作用域成一次 Apple Event**:
  当前这个页面只有**一个**混淆作用域(另一个是 icomoon,取字体失败、本来就不用映射),
  所以合并省不下什么;真要合就得改**两边共用的** `frame-bridge.ts` + `page-guard.ts`,
  风险落在"宁可留错字,绝不写错字"那条底线上。等真有"一页多个混淆字体"的场景再做。
- **判活查询缓存**(每轮都问一次,110ms):主通道慢下来不影响快通道,
  收益小于改动面,暂不做。
- **磁盘缓存字体分析结果**:分析只要 13ms,不值得。
