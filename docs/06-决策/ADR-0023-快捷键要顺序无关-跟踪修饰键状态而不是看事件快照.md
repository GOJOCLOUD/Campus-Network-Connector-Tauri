# ADR-0023:快捷键要「顺序无关」—— 跟踪修饰键状态,而不是看事件快照

- 状态:已定(Tauri / macOS 已实现)
- 日期:2026-10-23
- 相关:ADR-0022(快捷键「从来没被吞过」)、ADR-0020(按快捷键就崩)

## 背景

ADR-0022 修完"吞键"之后,用户仍然不满意:

> 「现在其实和最初没有区别,最初的 electron 版本就差不多是现在的这个效果,
> 然后最大的问题是什么?**它的容错太低了,非得三个同时一起按,才有这样的效果。**
> 有的时候他可能有一点误差,可能是个有顺序的,你所以要都要考虑到呀」

「三个同时一起按」= **⌃ + ⇧ + A 三个键**必须同时在位才算数。
用户要的是:**按下的先后顺序、手上的微小误差,都不该影响触发。**

---

## 一、根因:判定只看"事件快照",没跟踪"修饰键状态"

原来的判定(`match_hotkey`)只看**主键 keydown 那一瞬间事件自带的 flags**:

```rust
let flags = event.get_flags();          // ← 事件到达那一刻的快照
if !shift || !(ctrl || cmd) { return None; }
```

问题是**事件到达的顺序不确定**:

```
用户三个手指几乎同时落下
        ↓
硬件扫描顺序决定事件顺序 —— 主键的 KeyDown 完全可能**先于**
修饰键的 FlagsChanged 到达 tap
        ↓
那一刻事件自带的 flags 里,**修饰键还没有** ⇒ 匹配不上
        ↓
① 快捷键**根本不触发**
② 那一键还**漏给前台应用** ⇒ 用户看到"多打出一个 D"
```

⇒ **只有当三个键真正"同时"、扫描顺序恰好让修饰键先到,才匹配得上。**
这就是"非得三个同时一起按"的机制。

---

## 二、修法:自己跟踪修饰键状态

### ① tap 要听 `FlagsChanged`

每次修饰键按下/松开,macOS 都会发一个 `FlagsChanged` 事件,里面带**新的完整
修饰键状态**。把它加进 tap 的 mask,就能自己维护"当前按住了哪些修饰键":

```rust
vec![
    CGEventType::KeyDown,
    CGEventType::KeyUp,
    CGEventType::FlagsChanged,
]
```

### ② 判定用「跟踪到的 ∪ 事件自带的」

```rust
fn effective_modifiers(tracked: CGEventFlags, from_event: CGEventFlags) -> CGEventFlags {
    tracked | from_event
}
```

两个来源各管一件事:

| 来源 | 解决什么 |
| --- | --- |
| **跟踪到的**(`FlagsChanged` 累积) | 按下有先后 —— 修饰键后到也能算数 |
| **事件自带的** | App 启动**之前**用户就按着修饰键(那个 `FlagsChanged` 我们根本没收到,跟踪不到) |

取并集 ⇒ **顺序不再是问题**。

### ③ 修饰键后补齐时,回头认已经按下的键

```rust
fn find_pending_hotkey(
    pressed: &[(i64, Instant)],
    modifiers: CGEventFlags,
    now: Instant,
    window: Duration,
) -> Option<(i64, Hotkey)>
```

`FlagsChanged` 到来时,更新修饰键状态,然后回头看**当前正按着的键**:
如果现在能凑成快捷键,就是它。

⇒ **"先按 A,再补 ⌃⇧"也能触发。**

### ④ 时间窗:防止误触发

没有时间窗的话,"按住 A 打字半分钟,后来按了 ⌃⇧"会被误判成快捷键,
白白触发一次回放(还会在屏幕上乱点)。

所以只有 **2 秒内**按下的键才认(`RECOGNIZE_WINDOW`)。人手连按三个键的间隔
远小于这个量级,不影响正常使用。

### ⑤ 触发过就把键从"正按着"里拿掉

不拿掉的话,修饰键再变一次(比如又按了 Fn)就会**重复触发**。

## 三、诚实的边界

### ① 修饰键补齐**之前**先按下的那一键,已经漏出去了

macOS 的事件流是单向的:那一键的 KeyDown 已经交给前台应用了,
我们**追不回来**。

⇒ 所以"三个键**真正同时**按"时,快捷键**能触发**了,但那一键仍可能漏出去一次。

**完全���漏的用法**:**先按住 ⌃⇧,再按 A**(修饰键先到 ⇒ 主键事件自带完整 flags
⇒ 匹配 ⇒ 吞掉 ⇒ 一点不漏)。这也是更省力的按法 —— 不用三个手指同时砸。

### ② ⌘⇧ 也会被认成快捷键

`match_hotkey_raw` 认 `ctrl || cmd`,所以 **⌘⇧A 也会触发「默认执行」**,
而 ⌘⇧A 在 Chrome/Safari 里是「新建标签页」—— 会被抢。

界面文案写的是 `Control+Shift+A`,严格说**只该认 ⌃⇧**。
但「收窄能力」按规矩要单独授权,所以**本轮保持现状**,记在这里待拍板。

### ③ Electron 线没动

它用系统热键(`globalShortcut.register`),修饰键对不上就不触发、按键照漏 ——
**顺序容错在那边同样没有**。根治要改成自建 tap,留作单独一轮。

- 新增 3 条单测(全是**纯函数**,不构造 `CGEvent`、不碰系统):

  - `太久的键不认` —— 超过 2 秒的键不再认

- 变异自检:
  | 变异 | 被哪条抓住 |
  | --- | --- |
  | M1:时间窗失效(太久也认) | `太久的键不认` |
  | M2:不取事件自带的修饰键 | `有效修饰键取并集` |
  | M3:回头认时无视当前修饰键 | `修饰键后补齐也能触发` |

## 五、教训

**"能力"和"证据"要分开验。** ADR-0022 里,自检验的是"tap 有没有认出这个组合键"
(匹配),而用户真正抱怨的是"认出来了,但按键还是漏了"(吞)。
这两件事共用一个看起来像"已验证"的证据 —— 结果只验了一半,另一半一直坏着。

**事件驱动的判定,不要只信"事件快照"。** 顺序敏感的问题,根子通常在
"用某一瞬间的快照当状态"。**自己跟踪状态**才是稳的。
