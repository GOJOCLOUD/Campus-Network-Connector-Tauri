# ADR-0026:Windows 线不保留「默认执行(回放)」界面 + 红底白字横幅的成因 + Windows 偏卡顿的根因

- 状态:**已定**(用户 2026-10-24 明确指令)
- 日期:2026-10-24
- 相关:ADR-0012(平台功能范围)、ADR-0013(界面层逐字照搬 Electron)、ADR-0025(Windows 线与 macOS 线行为对齐)
- 性质:**修订 ADR-0012 的 Windows 线范围**,并记下同批修掉的两处缺陷。

## 背景

2026-10-24 用户在 **Windows 版**上提了三件事:

1. Tauri 版「页面摘除不够干净」—— 多出一个**不能执行**的「默认执行」界面;
2. Tauri 版对这个**本来就没有的功能**显示**红底白字**提醒,要求去掉;
3. Electron 版没有红底白字问题,但**一样多了一个界面**(与 Tauri 相同);
4. Tauri 版**偏卡顿**。

(第 4 条是查前三条时顺带定位到的根因,用户没展开说,但同批修掉。)

三条现象的根因都**不是"忘了删"**,而是**代码里的说法和实际能力对不上**。逐条记在下面。

---

## 决策一:Windows 线不保留「默认执行(回放)」界面(修订 ADR-0012)

### 背景

ADR-0012 当时写的是「Windows 上已有的『默认执行(回放)』**保留**」,理由是
「录制文件是跨平台 JSON:macOS 录 → Windows 回放」。

**这个前提在 Windows 版上并不成立**:

- Windows 线**不做录制**(ADR-0012 原文就写着),Windows 上根本录不出文件;
- 界面上也没有「选择录制」的文件可挑 —— 「管理录制文件」那一档入口
  **挂在这个页面上**,页面撤掉,入口也跟着没了;
- ⇒ Windows 上的「默认执行」= 一个**没有源、点了没反应**的死界面。

### 决策

**Windows 线不保留「默认执行(回放)」界面。**

Windows 的界面步骤变成 **2 步:激活 → 键盘输入**(拼音自动键入)。

| 平台 | 界面步骤 |
| --- | --- |
| macOS | 1 激活 → 2 默认执行 → 3 模拟点击 → 4 键盘输入 |
| Windows | 1 激活 → 2 键盘输入 |

### 影响

| 项 | 之前 | 之后 |
| --- | --- | --- |
| Windows 界面步骤数 | 3 | **2** |
| Windows 的「默认执行 / 选择录制 / 管理」 | 在界面上 | **不出现** |
| macOS 侧 | 4 步 | **不变** |
| macOS 的「管理录制文件」入口 | 挂在「模拟点击」那一步 | **不变**(入口本来就在那边) |

### 待拍板(本轮没有替他做决定)

**⌃S 全局快捷键仍然注册在 Windows 上**,而它驱动的正是「默认执行」。
现在这一屏在界面上已经没有了,于是 ⌃S 变成一个**驱动看不见的动作**的全局键,
而且它会**抢走别的 App 的 Ctrl+S**(这是早就挂着的待拍板项)。

本轮**没有**动它 —— 改全局键属于减功能/改行为,要有单独的明确授权。
两条路,等拍板:

- **撤掉 Windows 上的 ⌃S**:界面上没有了,快捷键也不该有;顺带不再抢 Ctrl+S。
  ⌃D(读剪贴板并键入)保留 —— 那条走的是「键盘输入」,是真功能。
- **保留 ⌃S**:那就得承认 Windows 上「录制文件跨平台回放」这条路还有效,
  与 ADR-0012 的「Windows 不做录制」口径其实自相矛盾,得另写一条口径说清楚。

## 决策二:红底白字横幅的 `ok` 字段口径 —— 「原生模块能不能用」,不是「是不是 macOS」

### 根因

界面顶部那条红底白字横幅的显示条件是 `nativeStatus.ok === false`,
文案是「模拟输入相关功能不可用:原生模块加载失败(…)。请重新安装最新版安装包。」

两个框架给的 `ok` **同名不同义**:

| 实现 | `ok` 的实际含义 | Windows 上的取值 |
| --- | --- | --- |
| Electron `main.js` | `ok: !!native` —— **原生模块加载成功没有** | `true`(win-input 加载得好好的)⇒ 不显示 |
| Tauri `commands/app.rs` | `cfg!(target_os = "macos")` —— **是不是 macOS** | **恒为 `false`** ⇒ 横幅**必然出现** |

⇒ Tauri 的 Windows 版上,那条「原生模块加载失败」是**假消息**:
Windows 的原生模块(`SendInput` / 剪贴板)加载得好好的,「模拟输入」是能用的。
用户的话很准:「本来就没有这个功能 干嘛红底白字提醒」。

### 决策

**`ok` 的口径统一为「原生模块能不能用」**(与 Electron 一致):

- `NATIVE_MODULE_SUPPORTED = cfg!(any(target_os = "macos", target_os = "windows"))`;
- 命令能调到 ⇒ 原生模块编译进来了、注册成功了
  (真加载失败的话这条命令压根不会被注册,前端 `invoke` 会抛**异常**,
  而不是拿到 `ok:false`);
- `error` 只在真有问题时有内容(Electron 那边是 `nativeModuleError`,空串 = 没问题)。

⇒ **横幅不是死代码**:模块正常 ⇒ 不出现;模块真坏了 ⇒ 出现,而且写明原因。

### 门禁

- Rust 单测 `native_status_tests`:`ok` 必须等于「本平台有没有原生模块」,
  且 macOS / Windows 上必须是 `true`(Windows 的 CI 会跑这条);
- 界面门禁 `verify-ui-platforms.cjs`:桩里 `ok:true` ⇒ 横幅**不出现**;
  桩里 `ok:false` ⇒ 横幅**出现**且写明原因。两种都验。

## 决策三:Windows 偏卡顿的根因 —— 窗口高度与视口高度互相决定

### 根因

Tauri 版有一个 Electron 版**没有**的机制:**窗口贴合内容**
(`src/tauri-bridge.js` 的 `fitWindow` → 原生命令 `window_fit_to_content`
→ `w.set_size`)。它的作用是把透明窗口收到只剩白色卡片那么高
(否则窗口周围那圈透明区域**照样吃鼠标事件**,底下的 App 点不动)。

内容区(Stepper 里那个 `overflow-y:auto` 的容器)的 `max-height` 是 **`65vh`** ——
也就是**跟着窗口高度走**。于是「量窗口该多高」变成了一个圈:

```
窗口高度 → 65vh → 内容区高度 → 卡片高度 → 想要的窗口高度 → 窗口高度
```

每绕一圈就是一次**原生窗口尺寸变化**(WebView 整页重排;Windows 上还是
透明 + 无边框 + 置顶窗口,代价更高)。肉眼看到的就是「切一步、窗口抖好几下」。

**为什么只有 Windows 卡**:Windows 的窗口起始高度是 **320**
(macOS 与 Electron 都是 640),内容装不下,于是要一格一格往上爬(推导值,非实测):

```
320 → 440 → 518 → 532   (每次都是一次整页重排)

> ⚠️ 这一串是**按公式推导**的(内容区那个 65vh 的上限随窗口高度线性放大,
> 一格一格往上收敛),**不是在 Windows 真机上量出来的** ——
> 本仓库的验证环境是 macOS。真机上怎么量见下面「怎么验证」。
```

macOS 从 640 起步,内容区装得下 ⇒ 一次就到位。

### 决策

1. **要算的是「内容的自然高度」**,不是「当前窗口里渲染出来的高度」——
   前者与窗口高度无关,一次就算准,不会来回抖;
   切步骤的 0.4s 动画里卡片高度一直在变,但算出来的目标高度始终是同一个值
   ⇒ **动画期间不会再触发任何 resize**。
2. **Windows 窗口起始高度 320 → 640**(与 macOS / Electron 对齐),
   去掉「启动时内容装不下」这个状态。
3. **目标高度没变就不再叫原生改窗口** —— 原生那边每次都要查一次屏幕尺寸
   (`current_monitor` 会枚举显示器),不是免费的。

### 怎么量的

内容区里那个 `position:absolute` 的滑页容器,它的 `offsetHeight` 就是内容的
真实高度(不受外层 `max-height` 影响);`scrollHeight` 同理。

### 怎么验证

- 原生侧记一个 `FIT_RESIZE_COUNT`:**实际**改过几次窗口尺寸,
  出现在 `get_native_status` 的 `fitResizes` 字段里
  ⇒ 前端每 3 秒写的 `diag.json` 会带着它。
- 排查「Windows 上偏卡顿」时先看这个数:切一步应该只 +1。

### 范围

这一条**只改 Windows 线**(`src/tauri-bridge.js` 的 win 分支副本)。
macOS 线有同样的圈,但它的窗口起始高度够大、一次就到位,本轮不动
(改动会让已交付的 mac 包变旧,属于范围外)。
⇒ macOS 线那个潜在缺陷记在 `docs/05-运维/已知限制与失败场景.md`。

## 验收

- **界面**:Windows 渲染 **2 个步骤**;界面上没有「默认执行」「选择录制」「管理」;
  第 2 步是「键盘输入」且有「开始输入」按钮;没有红底白字横幅
  (`tools/verify/verify-ui-platforms.cjs`,两个框架各一份)。
- **原生状态**:`ok` 的口径单测通过(`cargo test --lib`)。
- **卡顿**:`diag.json` 里 `nativeStatus.fitResizes` 在切步骤时**只 +1**。
- **macOS**:界面步骤仍是 4 步,「管理录制文件」入口仍在「模拟点击」那一步。
- 两线各跑各的自检,各发各的包;**一边的绿不替另一边背书**。
- ⚠️ **Windows 真机行为仍未经真机验证**(本仓库的验证环境是 macOS)。
  CI 只证明「编得过 + 门禁过」。
